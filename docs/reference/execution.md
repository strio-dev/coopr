# Coopr execution contract

Coopr uses ordered KDL v2 instructions in `.coopr` files. A definition with no
`extend` builds a container; a definition with at least one `extend` builds
a component. This reference describes supported execution semantics. The CLI builds standalone and
component-consuming images and builds selected components with immutable
package snapshots. Images are retained in Coopr's local `containers/storage`
graph and components in its local OCI store;
the result can also be tagged locally or copied to an OCI archive, registry, or
supported image-engine store. Project-owned specification identifiers use
`coopr.strio.dev`.

## State and stages

A stage state consists of a Linux root filesystem, logical image configuration,
target platform, and declared argument scope. Instructions in a stage run in
source order. A `from` starts from an external OCI image, `scratch`, or a named
stage. A named stage supplies its filesystem, configuration, and platform at
the point where that stage ends. An external image supplies its own image
configuration. `scratch` starts with an empty filesystem and empty image
configuration. `package as="name"` starts with an empty filesystem and empty
image configuration. Its resulting filesystem and configuration are saved
together: `from "package-stage"` inherits both, while `copy`/`add` with
`from="package-stage"` takes only files. A package's configuration is never
installed into the caller merely because the component references that package.
`extend` starts from the consumer's current filesystem and image configuration.
Multiple `extend` stages start independently from the same consumer state. A
later `from` can continue one of them.

`--build-context NAME=VALUE` supplies a named local directory, image
(`docker-image://REFERENCE`), or selected OCI layout
(`oci-layout://PATH:TAG`). It also accepts public HTTP(S) tar archives and
HTTP(S), `git://`, `ssh://`, or SCP-style Git repositories. Git query selectors are `branch`, `tag`, or
`ref`, optional `subdir`, and optional `checksum`/`commit`; legacy
`#ref:subdir` fragments remain accepted. Private HTTP(S) Git uses host-scoped
`GIT_AUTH_HEADER.<host>` or `GIT_AUTH_TOKEN.<host>` secrets. SSH Git requires
`--ssh default` plus `GIT_KNOWN_HOSTS.<host>` or `GIT_KNOWN_HOSTS`. A name used
by `from`, `copy`/`add from=`, or a
`run` mount `from=` takes precedence over an image reference. When it matches a
stage alias, the context replaces that stage and skips its authored body;
numeric stage references still select stages. Only contexts used by the
selected graph are materialized. Local named contexts select their own
`.cooprignore`, `.containerignore`, or `.dockerignore` and freeze their contents before execution. Component build
contexts apply to package production; invocation-time local inputs come from
the caller build.

Portable state identity hashes the effective root filesystem and logical image
configuration, independent of layer boundaries. It includes file contents,
types, permissions, owners, links, xattrs, and nanosecond mtimes for every path
except `/`. The root directory's mtime is generated by the builder snapshot
mount, changes even after a no-op `RUN`, and is absent from the OCI layer tar;
only that timestamp is excluded. Root permissions, owner, and portable xattrs
remain significant to Coopr's captured state, sidecars, caches, and package
payloads. Ordinary image commits inherit a limitation observed with Buildah
1.43.2 and Podman 5.8.4: a changed root-directory mode, owner, or portable xattr
may be discarded when the image layer is committed. Coopr accepts the build
even when the committed image cannot represent those changes.

The logical configuration hash excludes `rootfs.diff_ids` and `history`, which
describe layer provenance; Coopr must retain the complete original image
configuration and layer descriptors for the resulting image.

Only Linux platforms are accepted. Each requested `--platform` sets the
default for one independently planned image build; a `from platform=` may
select a different Linux platform for an external stage. The plan's platform
reports the selected output stage's actual platform. `coopr build` accepts
repeated or comma-separated platform values. One value produces a
single-platform manifest. Several values produce one OCI image index, or one
Docker manifest list with `--format docker`, whose child descriptors retain the
requested platform order. Duplicate normalized output platforms are rejected.
`coopr component build` accepts the same repeated or comma-separated platform
selection. One value produces a component manifest. Several values produce an
OCI index whose children are complete single-platform component artifacts in
the requested order. Component resolution selects a child by the consumer's
platform before invocation.

When a `run` executes binaries for an architecture different from the host,
the host must provide a matching userspace emulator through
`binfmt_misc`; Coopr does not register one. Filesystem and metadata operations
that do not execute target binaries do not require emulation.

A container build's output is its final stage unless `--target` names another
stage. A component's selected output must descend from an `extend` through
`from` links. Component build fixes that output; invocation cannot select another
target. The selected output and its transitive stage dependencies form the
stored definition. A component call replaces the caller's current stage
state with the selected output state, then the caller continues with its next
instruction. Component references identify stored component outputs; an invocation
property named `target` is an ordinary argument, not a selector.

A component call replaces the caller filesystem and image configuration with
the selected output. The caller's declared arguments remain in scope; the
component's private arguments do not enter that scope. Returned image `ENV`
values overlay caller arguments and win name collisions. A later caller `arg`
declaration again uses the original caller CLI override. The call acts like a
`FROM` boundary for configuration: `ENTRYPOINT` after the call clears an
inherited `CMD` unless a later `CMD` supplies one. An `extend` is not a `FROM`
boundary for Docker `ONBUILD` semantics, so it does not consume the caller's
stored triggers.

A `from` stage executes inherited `ONBUILD` triggers before its authored
instructions, in the stored order, and removes the consumed triggers from the
child configuration. A trigger's local `COPY`, `ADD`, or bind-mount input uses
the child build's context. Standalone builds plan inherited `ARG` values and
stage references from selected external and local bases before scheduling.
Package production binds inherited references before execution. A direct
`from` of a verified package snapshot at invocation binds its configuration
before planning. Component publication retains named stages that an inherited
trigger could activate later, including immutable package snapshots that are
otherwise outside the selected output closure. An invocation-only external
base remains unresolved during publication. Invocation selects it before
closing the graph, plans its inherited `ARG` and stage references from the
verified configuration, and pins that immutable selection for execution.
Inherited stage references must name a retained, earlier stage.

`copy` and `add` with `from="stage"` add dependency edges but do not change the
current stage's base lineage. When `from=` names an external OCI image instead,
planning resolves it by platform to an immutable selected descriptor and
execution copies from the imported image filesystem. The selected image is an
input to instruction and component cache identity. All graph edges must be acyclic,
and stage names must resolve unambiguously. Graph-affecting arguments must
resolve before execution. Component build records their stage-versus-external
bindings for retained stages: invocation cannot reinterpret a pruned stage
name as an external image, change a stage dependency, or turn `scratch` into
an external image. An external image reference may vary through an invocation
argument only while remaining an external image; OCI resolution will then
select and verify an immutable descriptor for that operation. Component references may also use
caller ARG or ENV values; component build leaves these invocation-only references
unresolved and resolves them in the caller's maintained argument scope at call
time. FROM, COPY/ADD, and RUN mount `from=` roles are fixed in the published
graph. The planner treats a RUN mount `from=` as a named-stage dependency or
an external image input; the direct Buildah executor binds its immutable
storage image at execution.
If a deferred component can change the scope needed to classify a dynamic COPY
or mount source, including through a later FROM stage, component build rejects
that unknown role rather than freezing a provisional value. Literal sources
remain usable after such a call.

## Component build and invocation phases

Component build executes each required `package` stage and the stages it depends
on, then stores immutable package filesystem and configuration snapshots with
the selected component metadata. A package producer cannot depend on an
`extend` stage because the
consumer root filesystem is unavailable during component build. Packages outside
the selected output's dependency graph are excluded. Invocation loads required
package snapshots as input leaves and does not rerun their producers. A stage
derived from a package may still execute at invocation if the selected output
needs it. A private stage needed during component build and invocation may
execute separately in both phases; its local file inputs come from that phase's context.
The artifact retains the invocation graph; private producer instructions are
omitted because package snapshots already contain their results. A producer
referenced directly by invocation remains in that graph and executes there.
The current package adapter exports a flattened OCI snapshot with one
uncompressed tar layer and its full raw image configuration; even an empty
filesystem yields a canonical empty snapshot layer. Import checks the blob
digest, size, config diffID, and full normalized Linux platform, including OS
version and features, then imports the OCI layout into the private execution
store. Producer executions carry their declared local mounts and imported OCI
inputs; Coopr's resolver supplies registry credentials for pulls.
`from` inherits its configuration; `copy` reads only its files. The adapter
captures root mode, ownership, and portable xattrs in the package payload
snapshot so flattening does not erase them. Unsupported non-root xattrs still
fail explicitly. This is an immutable stored package snapshot. The local
instruction cache does not substitute for package snapshots or component
invocation caching.

`coopr component build FILE --cache oci-layout:PATH` and
`--cache registry:HOST/REPOSITORY` use the selected cache for reads and writes.
`--cache-from` permits reads only and `--cache-to` permits writes only; each is
repeatable and can name OCI layouts or registry repositories. These caches can
restore eligible completed package snapshots before opening a Buildah execution store. A hit requires every
selected package output; otherwise Coopr executes package production normally
and publishes the completed outputs. The versioned key covers the ordered
producer closure, fixed package arguments, immutable image and named-context
inputs, filtered local context when used, target platform, and
executor/lowering identities.
Package-result caching is independent of the local instruction cache. It
supports conventional networked RUN and declared bind, cache, tmpfs, secret,
and SSH mounts. Credential bytes, cache-mount contents, and network responses
do not invalidate these results; use `--no-cache` or an authored argument to
refresh them. Checksum-pinned remote ADD is eligible. Producer graphs with
unpinned remote ADD, nested component invocation, or host/insecure/device RUN
bypass whole-package reuse when their input or authorization closure is
incomplete; eligible individual instructions retain their own checkpoints.

Each component artifact must bind its selected output, target
platform, retained definition, fixed package argument values, package snapshot
descriptors (including configuration), and all bytes needed to invoke without
the component source checkout.
Multi-platform component selection uses a matching immutable artifact for the
consumer platform. Publication plans and builds package producers separately
for each requested platform, so automatic platform arguments and package
contents match the selected child. Architecture alone does not establish
distribution or package-manager compatibility. Internal planning data is not a portable
component artifact and does not prove immutable OCI input selection.

## Instructions and image configuration

Coopr owns the `component`, `extend`, and `package` instructions and the graph
and phase boundaries they introduce. Standard instructions apply in order. Coopr handles ARG/ENV expansion, shell and exec forms,
RUN mounts and network policy, COPY/ADD options, configuration mutation, stage
selection, and the layer boundary policy. Unsupported instructions or options
must fail explicitly.

Definitions preserve quoting, shell versus exec forms,
option values, and instruction order. Coopr also expands values used for
component parameterization, including SHELL, MAINTAINER, and structural
properties that BuildKit leaves literal. Equivalent Containerfile builds
provide behavioral comparisons for supported common behavior.

Supported instructions are `from`, `run`, `copy`, `add`, `arg`, `env`,
`label`, `workdir`, `user`, `cmd`, `entrypoint`, `shell`, `stopsignal`,
`expose`, `volume`, `maintainer`, `healthcheck`, and `onbuild`, plus Coopr's
component and package graph operations. KDL uses multiline strings for
multiline shell commands. Static COPY/ADD inputs remain ordinary build-context
files; generated content can use a shell heredoc inside a multiline `run`.
The primary context accepts a local directory, Git URL, or
HTTP(S) tar archive; remote named contexts remain separate inputs. `--file`
also accepts an HTTP(S) `.coopr` definition, independently of the context.
Definitions selected inside an archive or remote context stay within that
context after symlink resolution. An explicit local definition may live
outside the context, as with Containerfiles.

KDL string arguments keep their authored text until the builder evaluates it.
`run "echo $HOME"` is shell form. An `exec` child supplies the executable
and arguments without a shell:

```kdl
run {
    exec "/bin/sh" "-c" "echo hi"
}
```

CMD, ENTRYPOINT and HEALTHCHECK use the same forms: one shell-command string
or one `exec` child. An instruction cannot combine the two forms. `exec`
is not a top-level instruction. RUN mounts and devices remain sibling children;
healthcheck timing stays on the parent. Bare CMD/ENTRYPOINT or an empty `exec`
child clears that image setting.
Multiline RUN scripts beginning with `#!` retain their declared interpreter,
as with executable Containerfile heredocs.
String-valued options use string properties. Boolean options accept quoted
`"true"`/`"false"`; bare `true` and `false` are not valid KDL v2 values. Numeric
options use numbers, and file modes use quoted Unix permissions, such as
`copy "a" "/a" chmod="0755" link="true"`. Repeatable options use ordered child nodes, for example
`copy "a" "/a" { exclude "*.md" "*.tmp" }`.
`copy` and `add` accept `link="true"` for an independent linked layer.
Coopr commits that layer before a later filesystem instruction so `run` and
subsequent copies see the linked files in source order.
`run` mount children remain ordered. The executor applies the resulting
operations directly after component composition binds stages and imported
package inputs. Multiline `run """..."""` covers multiline shell scripts.
The authored format has no special inline-content form: use an ordinary
context file and `copy`/`add`, or generate content with a multiline shell
`run`. Component definitions capture component-owned files in package-producing
stages and copy them from the stored package at invocation.

`run` mounts support `secret` and `ssh` with `id`, `target`,
`required`, `uid`, `gid`, and `mode` options; `secret` also supports `env`.
Supply sources through repeatable `coopr build --secret id=NAME,src=PATH`,
`--secret id=NAME,env=VARIABLE`, or `--ssh ID[=PATH]`; the same flags work on
`coopr component build`. Source paths and environment variable names cross
the supervised worker boundary, but credential bytes are read only when the
RUN or authenticated remote ADD executes and are never added to the definition
or cache key. RUN instructions with secret or SSH mounts use the ordinary
instruction cache: the mount declaration affects the key, while the secret
value, agent contents, and local source path do not. As with other build tools,
refresh the cache when changed credentials must change the result.
`add` supports Git repositories through Coopr's Git fetch path, with
`keep-git-dir="true"` to retain `.git`. It accepts `unpack="true"` or
`unpack="false"` for archive sources. SSH and scp-style Git URLs use `--ssh default` and an explicit
`GIT_KNOWN_HOSTS[.host]` secret for strict host-key verification.
HTTP file sources can use request-scoped `HTTP_AUTH_HEADER_<host>` and
`HTTP_AUTH_TOKEN_<host>` secrets; credentials are selected for each redirect
host. Private HTTPS Git uses host-scoped `GIT_AUTH_HEADER[.host]` or
`GIT_AUTH_TOKEN[.host]` secrets. Authenticated Git fetches reject redirects.
The HTTP authorization header is scoped to the selected parent repository;
submodule URLs outside that scope do not receive it.
Git named contexts fetch nested submodules by default; `submodules=false`
disables that work, and `keep-git-dir=true` preserves Git metadata from the
parent and submodules. The `mtime=commit` query sets checked-out file times to
the selected commit time. `fetch-by-commit=true` requires a full lowercase
commit SHA in `checksum` and fetches that SHA directly. These controls are
named-context URL options; `add` retains its instruction-level `keep-git-dir`
option.
`copy` accepts local context or declared stage/image sources only and rejects
HTTP(S) and Git sources before connecting to them. `add` owns the explicit
remote-source behavior and its checksum policy.
Mount types and properties may use build arguments. The resolved mount type
is validated before execution.
`run` supports default, private, none, host, named networks, `ns:PATH`,
and Pasta/slirp4netns modes with their native options.
The build-wide `--network` value supplies the effective mode
for a RUN without an authored `network` property. An authored value, including
`network="default"`, wins. Resolution happens before entitlement checks,
scheduling, and cache eligibility or identity, and also covers inherited
ONBUILD RUN instructions and RUN instructions inside component invocations.
Thus an implicit RUN under `--network none` has the same scheduling and cache
behavior as an explicit `network="none"`. Default and entitled host modes use
conventional instruction caching without hashing network responses.
Host networking requires `--allow network.host`, including on a warm cache
hit; inside containerized Coopr, host means the outer Coopr container's
network namespace. Repeated `--add-host 'HOST[;HOST...]:IP'` entries add
normalized host mappings to RUN execution; `host-gateway` is accepted
as the address. Host mappings apply to authored, inherited, and component RUN
execution and enter local instruction, component-state, and package-result
cache semantics. Because `host-gateway` is resolved from the execution host,
its presence disables RUN instruction caching and component/package result
caching. `run security="insecure"` requires `--allow
security.insecure`, including on a warm cache hit. For that RUN, Coopr uses a
same-binary OCI runtime wrapper to apply the BuildKit insecure-spec policy to
Buildah's generated bundle before invoking the selected OCI runtime. Effective
privileges remain bounded by the outer container, user namespace, and kernel.
This mode requires OCI or rootless isolation; chroot isolation is rejected.
The runtime needs permission to remount `sysfs` and cgroups writable for this
mode. A nested rootless container can reject that mount even when Coopr grants
the entitlement; Coopr reports the runtime failure instead of silently using
the ordinary security profile.
CDI devices use child nodes such as `run "command" { device "vendor.example/gpu=card0" "vendor.example/gpu=card1" required="true" }`. A device requires `--allow device`,
`--allow device=SELECTOR`, or a CDI auto-allow annotation. Device selection and
authorization happen before cache lookup. Containerized Coopr can only pass
through devices and CDI files available inside its outer container.

`healthcheck` records the corresponding Docker image configuration:

```kdl
healthcheck interval="30s" timeout="3s" retries=3 {
    exec "/bin/check" "--ready"
}
healthcheck "curl --fail http://127.0.0.1/ready"
healthcheck NONE
```

The timing properties are `interval`, `timeout`, `start-period`, and
`start-interval`; `retries` is a nonnegative integer. `onbuild` contains exactly
one ordinary KDL instruction, for example `onbuild { run "make generated" }`.
Coopr compiles that child to the image configuration's required ONBUILD string
internally. When a later `from` consumes an image, Coopr parses the stored
instruction in memory; it does not render the build graph as a Containerfile.
Nested `ONBUILD`, `FROM`, and `MAINTAINER` are rejected as inherited triggers.
An inherited insecure `RUN` requires the same entitlement as an authored RUN.
Imported Docker image triggers can contain RUN, COPY, or ADD heredocs. Coopr
preserves their stored Dockerfile semantics, including empty or executable
shebang RUN scripts and delimiter-derived COPY/ADD filenames. This import
compatibility does not add raw Dockerfile strings or inline COPY/ADD forms to
the authored KDL syntax.
Inherited RUN secret and SSH mounts can use
the sources supplied to the child build.

`Healthcheck` and `OnBuild` are image-configuration extensions that Coopr
preserves with either OCI or Docker schema 2 output. A child consumes inherited
`ONBUILD` triggers before its authored instructions and clears the consumed
triggers from its own configuration. A receiving runtime may ignore these
extensions.

An instruction changing image configuration does not by itself change the
filesystem, but it changes the stage state and must invalidate a cached result
when output-relevant. `from` inherits configuration from its source, including
a package stage. `extend` inherits the caller's configuration. Copying files
from a package does not replace caller configuration. The selected adapter must
preserve OCI configuration fields it does not explicitly change. Unsupported OCI configuration or
filesystem metadata must fail explicitly if it cannot be preserved, except for
the documented Buildah/Podman root-directory commit limitation.


## Arguments and normalization

An `arg` before the first stage is global. A stage-local `arg` applies from
its declaration onward and passes to a stage that uses `from` to inherit it.
An independent `extend` starts with the caller filesystem and image
configuration, including image `ENV`, plus global and explicitly supplied
component arguments. It does not inherit the caller's stage-local `ARG`
environment unless those values are passed as component properties. Nor does
it inherit another `extend` stage's locals. A
component call preserves the caller's declared argument scope as described
above; component-local declarations remain private. A
package-producing stage fixes every argument in its effective scope at
component build, even if its command text does not mention that name. This is a
conservative fixed-argument policy for the current implementation. Invocation
cannot override those values. Invocation arguments declared after `extend`
remain adjustable unless they also affect package production.

Arguments are strings; no implicit number or boolean conversion occurs.
Standard ARG/ENV substitution and RUN exposure must match Containerfile
behavior after lowering. The planner expands supported shell-style variable
forms and maintains ARG/ENV scopes for component properties and structural
references.
Undeclared and unset ARG references expand to an empty string, and unused
supplied build arguments are ignored, following Dockerfile behavior. Structural
values, including `from` sources and `from=` stage references, still need to
be valid after expansion. Conflicting package values and invocation overrides
of fixed package arguments are errors.

`SOURCE_DATE_EPOCH` accepts a supplied Unix timestamp or a global `arg`
default. It affects image and history creation times without entering a RUN
environment until redeclared in the stage. An empty value clears it.
The special value `context` leaves it unset for a local primary context, uses
the selected Git commit's committer time for a Git primary context, and uses
HTTP `Last-Modified` or the newest regular-file archive mtime for an HTTP tar
primary context. An explicit numeric build argument takes precedence over an
authored `context` default. A named context value uses the same Git or HTTP
metadata rules; local, image, and OCI-layout named contexts leave it unset. A
stage name may also select a source-only stage. That stage must use `from
"scratch"`, contain only `arg` instructions and exactly one remote HTTP(S) or
Git `add`, and is resolved from that source's metadata.
`--source-date-epoch UNIX_SECONDS` explicitly overrides the resolved epoch.
`--timestamp UNIX_SECONDS` instead forces creation and new-layer file timestamps,
including older files and packaged component snapshots. It conflicts with
`--source-date-epoch` and `--rewrite-timestamp`. `--rewrite-timestamp` separately
clamps newer filesystem timestamps in OCI layers and component package snapshots.
Timestamp policies enter instruction and portable cache identities.
`--cache-ttl DURATION` bounds local and portable instruction, invocation, and
package cache reads by the record's publication time. Zero disables reads while
fresh results are still written; fixed image timestamps do not affect record age.

Component parameters must be valid UTF-8. For cache identity, string maps are encoded as JSON with sorted
keys. A missing key and a present empty string have different encodings;
nil and empty maps both encode as `{}`. Apply this encoding to component-build
and invocation arguments before hashing. The portable cache key is versioned
and includes the logical input filesystem and configuration, component OCI
digest, normalized invocation parameters, immutable package descriptors, full
Linux platform, and executor/lowering versions. The execution path
computes the key after resolving its measured inputs.

## Build contexts and local files

Every local `copy`/`add` source has a phase-specific context root:

| Phase | Local source root |
| --- | --- |
| Container build | The build caller's selected context. |
| Component build | The component builder's selected context, including files beside the component definition. |
| Component invocation | The consuming build caller's selected context, even when the instruction came from the component. |

`from=` changes the source to a stage or stored package and does not read a
local context. Component-owned files therefore need to be captured by a
package or its component-build producers. Invocation cannot rely on the
component source checkout. A `run` bind mount without `from=` follows the same
phase-specific local context rule. A mount with `from=` reads a named stage or
stored package stage, including one retained by a component artifact. Cache
mounts are separate disposable storage. The image and component build commands
select and snapshot these phase-specific contexts; internal planning alone
does not execute them.

Local context inputs exclude the host's `security.selinux` xattr, including
labels deliberately set with `chcon`. Those labels describe host policy and
are not portable image content. The transport retains other xattrs, including
`security.capability` and `user.*`, so the executor can preserve supported
metadata or reject unsupported metadata before export. This input rule does
not apply to OCI image/package snapshots or labels created by `RUN`; those
remain subject to the executor's output metadata checks.

The selected output archive when requested, Coopr stores, private execution
roots, package snapshots, and temporary worker paths are excluded exactly when
they lie inside the chosen local context. `COPY` and `ADD` cannot
read these active build artifacts; unrelated authored files remain available.
The selected ignore policy is applied while Buildah snapshots the context.

Coopr snapshots the selected context through its protected Buildah copy boundary. Standalone builds default to the definition's directory; invocation uses the caller's selected context and ignore policy. The effective filtered inputs contribute to cache identity. Local source paths and symlinks cannot escape the context.

## Build request controls

The primary definition and context are independent inputs. Either may use
stdin, but not both in one request. A context may be a directory, local tar
archive, stdin tar stream, Git checkout, or HTTP(S) tar archive. An explicit
`--ignorefile` wins; otherwise Coopr selects the first available file at the
context root: `.cooprignore`, `.containerignore`, then `.dockerignore`. The
selected file uses Docker/Podman ignore patterns and applies to local COPY,
ADD, RUN bind inputs, and local component definitions. Its effective filtered
inputs contribute to cache identity. Definition placement does not change
automatic ignore-file selection.

`--tag` is repeatable. Coopr completes and retains the build once, then applies
each local name or copy destination to that immutable result. `--metadata-file`
uses the established `containerimage.digest`, `containerimage.config.digest`,
and `containerimage.descriptor` keys plus `coopr.platforms`,
`coopr.references`, and per-destination `coopr.outputs`. Image builds also support `--iidfile`: one platform writes
the configuration image ID, while several platforms write the root index
digest. Engine-prefixed build destinations and `coopr
copy` use the same direct transfer implementations; image sources may also be
imported from an explicit Podman or Docker source. Component artifacts remain
outside engine image stores. An imported engine index must contain exactly one
runnable Linux image manifest per platform. Auxiliary descriptors such as
attestations and duplicate platform manifests are rejected instead of being
silently dropped from the retained index.

File output parents are checked before execution. An immutable build result
and its verified cache checkpoints are durable after successful execution;
destination transfers then commit individually in the requested order. External
registries and engines do not provide a shared transaction. If a transfer fails
or is canceled, the command fails and identifies the retained digest and
completed destinations. Requested metadata records complete, failed, and pending
destinations plus `coopr.outputError`; a failed destination may require checking
its engine or registry if the connection ended during commit. Retry an output
with `coopr copy` rather than rebuilding. A result-file finalization failure also
reports the retained digest and completed outputs. Execution failure never
publishes newly staged portable cache candidates or final output names.

Registry operations share one request-scoped authentication and trust policy:
`--authfile` accepts containers-auth.json or Docker config JSON,
`--cert-dir` contains `ca.crt` and optional client certificate/key files, and
`--tls-verify=false` disables verification for the referenced registry. When
no auth file is supplied, the standard containers/image and Docker credential
locations and helpers are used. The policy applies to image and component
resolution, portable cache repositories, and build/copy publication.

`--http-proxy` controls predefined host proxy variables passed to RUN.
Repeated `--dns`, `--dns-search`, and `--dns-option` values define resolver
configuration. Memory, memory-plus-swap, CPU period/quota/shares, `/dev/shm`
size, and ulimits apply to RUN execution. These
values are normalized before execution and enter instruction, component, and
package cache identities. Zero resource sizes are accepted; an explicit
`--shm-size=0` remains distinct from omission. Memory and swap values are
applied independently. An authored RUN network value takes precedence:
validation uses each effective
RUN mode, so explicit `network="default"` or `host` may override a global none,
while explicit `network="none"` rejects DNS controls under any global default.
Resource controls fail with a precise error when the rootless host lacks the
required cgroup version or controller delegation.

Both build modes expose host `--volume` binds, capability additions/removals,
security options, host/CDI devices, supplementary groups, user namespaces and
UID/GID mappings, PID/IPC/UTS/cgroup namespaces, cgroup parent, cpusets, OCI hooks,
runtime and runtime flags, and isolation.
The outer host's namespace, security policy, devices, and delegated cgroups
still determine which requests can run. Normalized settings enter cache keys;
seccomp and hook JSON content is hashed. Host volume/device contents are
conventional unmeasured inputs; `--no-cache` refreshes them.

Image `--env` values are prepended to every stage and available to RUN; authored
ENV wins. Bare names import host values when present, `PREFIX*` imports matching
names, and `*` imports the host environment. Repeated named contexts and
secret/SSH source IDs use the last supplied value. Label/environment unsets,
inheritance controls, and history omission
are applied to final outputs, including cache hits. Annotation changes apply to
OCI manifests; Docker format accepts the controls and drops annotations.

`--all-platforms` discovers common runnable Linux platforms across non-scratch
base images and conflicts with explicit `--platform`. `--manifest NAME`
serializes updates to a local named index, preserves other platform instances,
and replaces the instance for each newly built platform. The named index remains
consumable through the same image graph and copy paths.

`--jobs` is a nonnegative total budget across platform builds and independent
stages. The default is one; zero permits all dependency-ready work. The scheduler waits for dependency
outputs, including component resolution/package inputs and mounted stage or
image sources, before starting a stage; parallel work never changes graph
ordering or cache identity.

## Resolution, compatibility, execution, and caching

The following are separate contracts, regardless of which libraries implement
them:

1. **Resolution and planning** parse definitions, resolve image and component
   references by platform to immutable OCI digests, validate compatibility,
   bind arguments and contexts, and produce an ordered graph. Registry component
   tags resolve on each build. Registry image tags use the local cached selection
   by default. `--pull-policy missing|always|newer|never` makes that policy explicit,
   and `--pull` without a value selects `always`. `--pull=newer` compares
   selected digests and falls back to a local image on registry failures. Under `never`, a missing local image
   fails before registry access. A digest
   reference selects an exact object and can reuse its local copy offline.
   Reproducibility requires digest-pinning every selected OCI reference,
   including nested image and component references. Registry cache locations
   are runtime configuration, not authored definition fields.
2. **Execution** applies instructions in order to the selected image inputs
   and retains the resulting filesystem and image configuration in the selected
   image store.
3. **Caching** gives generated cache mounts deterministic names derived from
   the measured build or component scope, selected component digest, normalized
   arguments, target platform, stage, and mount settings. These mounts are
   local accelerators and cannot be required for correct output. Coopr also
   stores immutable local instruction-result images inside the selected image
   graph. Supported `run`, `copy`, `add`, and `workdir` instructions can hit in
   standalone and component-invocation stages, including the final instruction.
   Package production also uses this cache: root mode, ownership, and portable
   xattrs are captured and restored across checkpoints and cache hits. Metadata-only instructions update the logical image
   configuration without creating cache images; output-only changes can reuse
   prior filesystem results. The key includes the immutable parent image ID
   and selected manifest digest,
   execution-relevant configuration (environment, user, working directory,
   shell, volumes, and argument escaping), normalized planned instruction and
   arguments, target platform, isolation, Buildah version, and relevant input
   identities. `run` keys include the exact OCI-runtime binary identity and
   resolved mount inputs; secret and SSH mounts contribute their authored
   metadata, but credential bytes and agent state do not enter the key.
   Local and image-backed `copy` and `add` keys include Buildah's source-stream
   digest; eligible copies probe before lookup. Checksum-pinned HTTP ADD uses
   its validated authored SHA-256 before lookup and verifies downloaded bytes
   on a miss. Git ADD uses the resolved full commit after cloning, checksum
   validation, and recursive submodule checkout. It applies before lookup,
   then replaces the temporary result on a hit. Clone timestamps and generated
   Git metadata do not invalidate it. Other remote or linked operations retain
   the apply-first path.
   Network responses, clock, randomness, and other undeclared inputs remain
   outside reproducibility guarantees. `--no-cache` bypasses reads from local
   instruction, portable component-state, and package-result caches while
   recording newly executed results and leaving cache mounts intact. Optional
   OCI layout and registry caches also publish exact
   OCI checkpoint image graphs for eligible instructions. Their key uses
   the selected parent OCI manifest digest instead of a private store ID;
   networked RUN and declared mounts, local/stage/image/named-context COPY/ADD,
   checksum-pinned remote ADD, and WORKDIR are eligible when declared input
   identities are complete. Unpinned remote ADD and device-backed RUN remain
   local-cache-only. Component invocation
   states and completed package snapshots use separate OCI artifacts.
   `--cache` enables reads and writes, while `--cache-from` and `--cache-to`
   authorize only the named direction. A validated read hit can seed a separate
   writable destination, but a read-only source is never updated and a
   write-only destination is never queried.
4. **Assembly, storage, and publication** use the selected OCI or Docker
   schema 2 output while preserving original base layers and configuration. The
   target policy is one
   layer for each filesystem-changing ordinary instruction and one net layer
   for a filesystem-changing component invocation. Configuration-only or empty
   changes add no layer. Inspect the emitted descriptors and diffIDs to
   prove this policy, including deletions, directory opacity, and type changes.
   Package layers are inputs to invocation, not automatically appended to the
   consumer image. Component build binds metadata and package snapshots into
   one OCI artifact before local storage, archive output, or registry publication.

`coopr build` stores every final child image in the selected native
`containers/storage` graph. By default this is Coopr's graph under
`$XDG_DATA_HOME/coopr/images`, or `~/.local/share/coopr/images` when
`XDG_DATA_HOME` is unset. The optional XDG `coopr/config.toml` setting
`image-store = "podman"` selects Podman's effective configured graph instead;
the global `--image-store coopr|podman` flag overrides it. Native storage flags
override that selected configuration. Components keep their own Coopr OCI
store. Docker remains an explicit transfer source and destination. Registry
pulls, image inputs and outputs all use the selected graph. In Podman mode,
native mutable image names are authoritative and ordinary output tags are
visible to Podman. The catalog records selected immutable manifests instead
of duplicating image layers.

For a multi-platform build, its catalog additionally
retains the exact index bytes and maps the common root descriptor to every
child platform. Without a tag the command returns the canonical root digest,
which is a manifest digest for one platform or an index digest for several. A
local tag returns the ordinary tag. `--format
oci` is the default; `--format docker` selects Docker schema 2 manifest and
configuration media types and, for several platforms, a Docker manifest list.
The executor exports each selected representation through a private temporary
layout, verifies its descriptors, imports it into the same image graph, and
records the exact manifest and raw configuration in the catalog. Default
storage and engine-copy paths do not persist an intermediate archive or
layout.

An explicit `--tag` transport selects a post-build copy destination:
`local:`, `oci-archive:`, `registry:`, `podman:`, or `docker:`.
Unprefixed names mean `local:`. `--push --tag NAME` also selects a registry
destination. A single-platform destination starts from the exact selected
platform image retained in the selected native store. A multi-platform registry, OCI
archive, or Podman destination receives the complete assembled index and all
child image graphs. A later `coopr copy` re-exports the stored object and
requires each manifest descriptor and the root index descriptor to match the
catalog before transfer.
Destination engines can still apply their own conversion rules. Docker may
convert default OCI output to Docker schema 2; selecting `--format docker`
avoids depending on that conversion.

`coopr copy LOCAL-REFERENCE DESTINATION` applies the same destination operation
to an already-built image. Its source is an ordinary local tag or a bare
`sha256:<digest>`. Copying into an engine store is explicit; default output does
not require an engine socket. The embedded image graph is accessed through
Coopr's supervised rootless worker. When the source identifies a complete
locally built index and `--platform` is omitted, a local destination preserves
the complete index under the new tag and registry, OCI archive, Podman, or
Docker's containerd image store destinations receive the complete index.
An explicit `--platform` selects and copies one child manifest. Docker's
classic image store requires this explicit platform selection for a
multi-platform source. Coopr checks the daemon's store capability before
uploading an index, then verifies its root digest and available platform
manifests after loading it.

Registry indexes from which Coopr has imported only selected children are
partial catalog records, not complete locally built indexes. Their tags and
index digests default to the native Linux selection. A local tag with one
stored platform selects it automatically. A bare single-platform manifest
digest selects that exact manifest regardless of the host platform.

`coopr component build` stores the component in Coopr's engine-neutral OCI
layout by default. The layout is rooted at `$XDG_DATA_HOME/coopr/components`,
or `~/.local/share/coopr/components` when `XDG_DATA_HOME` is unset. Without a
tag the command returns `sha256:<digest>`; a local tag returns the ordinary tag.
Invocation accepts a bare digest as an immutable local pin or an explicit
`local:<tag>` reference, and does not try the local store when a registry
reference fails. `--tag oci-archive:PATH` writes a component OCI archive copy;
`--tag registry:REGISTRY/REPOSITORY:TAG` publishes a registry copy and returns
its immutable registry reference. `coopr component copy LOCAL-REFERENCE
DESTINATION` retags or copies an existing component without rebuilding.
Component destinations are limited to `local:`, `registry:`, and
`oci-archive:` because component artifacts are not engine-loadable images.

An `extend` may declare `distro`, `distro-version`, `package-manager`, and
`architecture` as string properties or child nodes containing allowed string
values:

```kdl
extend as="base" {
    distro "fedora" "rhel"
    distro-version "41" "42" "9"
    package-manager "dnf" "yum"
    architecture "amd64" "arm64"
}
```

Scalar properties are singleton allow-lists. A field may be declared once;
mixing its property and child forms or repeating its child is an error.
Lists must contain at least one nonempty string. Their `${name}` values use
the global ARG expansion available to structural `from` values. Planning
normalizes architecture aliases, removes duplicate values, and sorts lists
so their order does not change the normalized execution-plan identity. The
published OCI component digest still identifies its exact authored definition;
reordering authored children can therefore change that artifact digest.

Any value within a field may match. All declared fields and retained `extend`
roots must match, including when the selected output descends from several
roots. `distro-version` requires `distro`; omitting it accepts any version of
an allowed distro. At invocation, Coopr checks all roots against the caller
before running any component-body instruction or using a portable component
cache hit. Published definitions retain the lists and argument expressions.

`architecture` must match the selected normalized Linux OCI platform's
architecture. `distro` matches an exact allowed `ID` in the caller's `/etc/os-release`;
Coopr reads `/usr/lib/os-release` only if `/etc/os-release` is absent.
`distro-version` additionally matches an exact allowed `VERSION_ID`. Coopr does not
infer matches from `ID_LIKE` or accept version ranges. `package-manager`
requires at least one allowed executable file in the caller filesystem. It accepts an absolute
path or a simple program name searched in the image's absolute PATH
directories, with conventional defaults when PATH is absent. A missing or
conflicting required value fails the invocation. Manager version checks are
not part of this declaration. A compatibility check that reads the caller
filesystem may cause an early solve at that component boundary; independent
stages without such requirements remain independently schedulable.

Cache mounts are disposable accelerators, not required component payload.
Correct output must be possible with an empty mount. RUN uses the build-wide
network default unless an authored per-instruction policy overrides it;
host networking still requires its entitlement. An optional OCI component-state
cache can reuse selected `extend` results across builds and machines. It keys
the caller rootfs, component digest, parameters, immutable package inputs,
platform, and executor semantics. Declared package/stage/image sources and
mount properties enter the key; mutable network responses, secret values,
SSH agent state, and cache-mount contents conventionally do not. Invocation-time
caller-local context reads whose identities are incomplete exclude the
whole-component cache; eligible instructions can still cache individually. A
cacheable RUN uses the conventional build-cache assumption that the command is
deterministic for its measured inputs.
Clock, randomness, kernel state, and other undeclared host inputs are not
measured, so a hit is not a reproducibility guarantee. Required reusable
bytes belong in component packages. A cache repository is an opt-in trusted
input and needs the same or stronger access controls as intermediate rootfs
state, which may contain files absent from the final image.

Local names and usage are visible through `coopr image ls|inspect|rm`, `coopr
component ls|inspect|rm`, `coopr system df|prune`, and `coopr cache df|prune`.
Pruning protects named image roots, reports in-use objects it cannot remove,
and supports a dry run. Image commands maintain the selected canonical graph;
component commands maintain the separate Coopr component store. In shared
Podman mode, pruning protects unrelated native images and running containers.
Coopr's activity lease coordinates its own processes; external Podman access
uses containers/storage's native locking. Coopr does not prune Docker stores.
